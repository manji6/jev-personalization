# 取得・送信されるデータ

## 自動で観測するもの

利用者の同意を得て、サイト設定のメタデータ送信が有効になっている収集対象ページで観測します。以下のキーは、SDKが保持し、自前APIへの判断要求に使う名前です。

| 観測する値     | キー               | 取得元・単位                                                             |
| -------------- | ------------------ | ------------------------------------------------------------------------ |
| ページのパス   | `page.path`        | 現在のURLの`location.pathname`。例：`/products/polo`                     |
| ページの名称   | `page.name`        | 下記の優先順位で取得する文字列                                           |
| ページの説明   | `page.description` | 下記の優先順位で取得する文字列。取得できなければキーを省略               |
| ページの種類   | `page.type`        | カスタムのJSON-LD候補、または従来モードの`@type`。標準では省略           |
| ページのテーマ | `page.themes`      | カスタムのJSON-LD候補、または従来モードから取得。標準では省略            |
| 表示中の時間   | `visibleMs`        | ページごとの累積ミリ秒。タブが非表示の間や`pagehide`後の時間は加算しない |
| 閲覧した順序   | `visits[]`の配列順 | 古い閲覧から新しい閲覧の順。直近50件を保持                               |

`visibleMs`はタブの可視状態に基づく時間で、実際に読んだ時間や注視時間を確認する値ではありません。1件あたりの上限は86,400,000ミリ秒です。閲覧ごとの日時・訪問ID・スクロール量は記録しません。

ページ情報は、初期判断用の`currentPage`と、最低閲覧時間を満たした`visits[].page`に使います。流入時のページは`entryPage`へ`path`・`name`・`url`を保存します。

### ページURLと除外キー

`page.url`は`location.href`から取得します。GETパラメータを含み、除外設定が空ならその値をすべて保持します。URL内のユーザー名・パスワード・`#`以降は常に除きます。`path`は従来どおりパスだけです。

「サイト設定 → ページ情報の取得」の**取得しないGETパラメータのキー**で、除外するキーを最大50件、1キー100文字以内で指定できます。URLデコードしたキーに対する、大文字小文字を区別した完全一致です。同じキーが複数あれば全て除きます。残すパラメータの順序とエンコードは維持します。

例：除外キーを`email`・`token`とすると、`https://example.com/polo?cid=mail_runner&email=a%40example.com&token=x#size`から保存・送信するURLは`https://example.com/polo?cid=mail_runner`です。`Email`は`email`と別のキーです。URLは4,096文字以内で、超える場合はURL項目を省略し、パス・名称を残します。

除外はSDKで保存・通常送信・診断記録の前に適用し、自前APIでも再検査します。除外した値を使うURL条件は成立しません。URL中の検索語や個人情報は自動で検出しません。パスに個人情報がある場合は除外経路を設定してください。

`entryPage`は、このタブで同意後に最初に観測した収集対象ページです。同意前の流入やHTTPのRefererから推測しません。後続ページに`cid`がなくても、保存した流入ページの`cid`を判定できます。

### 取得方法をサイトごとに選ぶ

「サイト設定 → ページ情報の取得」で、サイト管理者またはSuperuserが変更できます。新しいサイトは標準モードです。取得設定がない既存サイトは、切り替えて保存するまで従来のJSON-LD優先を維持します。

### 標準モードの取得優先順位

| 取得値             | 第1候補                                                                         | 第2候補                                                                   | 取得できない場合 |
| ------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ---------------- |
| `page.name`        | `meta[property="og:title"]`または`meta[name="og:title"]`の`content`             | HTMLの`title`                                                             | `Untitled`       |
| `page.description` | `meta[property="og:description"]`または`meta[name="og:description"]`の`content` | `meta[name="description"]`または`meta[property="description"]`の`content` | キーを省略       |
| `page.type`        | 取得しない                                                                      | —                                                                         | キーを省略       |
| `page.themes`      | 取得しない                                                                      | —                                                                         | キーを省略       |

名称と説明はそれぞれの順序で評価します。値が空、文字列でない、共通の除外パターンに一致する場合も次の候補へ進みます。標準モードはJSON-LDを読みません。メタタグは最大200要素を調べ、同じキーの最初の要素だけを使います。

### カスタムモードの取得優先順位

管理画面に並べた候補を上から評価し、条件とページ名を満たす最初の候補を採用します。候補は最大10件、各候補の条件は最大5つです。

例として、次の順序を設定できます。

| 順位 | 条件                                                                 | ページ名                           | 説明                       |
| ---- | -------------------------------------------------------------------- | ---------------------------------- | -------------------------- |
| 1    | JSON-LDの`@type`が`Product`を含み、同じオブジェクトの`sku`に値がある | `商品詳細：` + 同じJSON-LDの`name` | 同じJSON-LDの`description` |
| 2    | `og:title`に値がある                                                 | `og:title`                         | `og:description`           |
| 3    | HTML titleに値がある                                                 | HTML title                         | meta description           |

`Product`がschema.orgの標準です。`Products`や`ProductGroup`へ自動変換しません。条件はAND/ORと「値がある」「プロパティがある」「等しい」「配列に含む／文字列と一致」を選べます。0・falseは値として存在します。「等しい」と「含む」は文字列化した完全一致で、部分一致ではありません。

ページ名・説明の取得元、取得キー、取得値の前につける文字を選べます。説明が取れない場合は「説明なしで採用」か「次の候補へ進む」を指定します。どの候補も使えなければ、現在の`path`と`name: "Untitled"`を残し、説明を省略します。

JSON-LDの条件と取得値は同じオブジェクトで評価します。複数候補がある場合は、現在のページと一致するWebPageのmainEntity、現在のページに結び付くurl/mainEntityOfPageの順に、一意の対象を探します。特定できなければ次の候補へ進みます。先頭の商品を自動で選びません。

JSON-LD候補を採用した場合だけ、同じ候補の`@type`の最初の文字列を`page.type`へ、`articleSection ?? keywords`を`page.themes`へ使います。テーマは文字列または文字列配列を半角カンマで分け、最大8件です。空のarticleSectionからkeywordsへの切り替えや重複除去はしません。メタタグ・titleだけの候補ではtype/themesを省略します。

JSON-LDは先頭10本・1本100,000文字以下、探索深さ8、オブジェクト最大200件です。直下・配列・@graph・mainEntityを調べ、itemListElement内や外部参照は展開しません。キーは6段・120文字までの単純なプロパティ参照です。式・任意のJavaScript・DOMセレクターは使えません。条件確認用のsku等をAPIへ自動追加しません。

### 共通の整形と除外

名称160文字・説明400文字・種類80文字・各テーマ80文字までです。連続する空白・改行を半角スペース1つにし、前後の空白を除き、上限で切り詰めます。その後、メール形式や、空白・ハイフンを挟む形を含む9桁以上の数字列に一致する文字列を除外します。カスタムの接頭辞にも同じ検査を行います。

この検査だけで個人情報をすべて除けるわけではありません。氏名・住所・個人向けのメタ情報を含むページは、収集経路から除外してください。

### 設定変更と実ページでの確認

SDK本体は共通です。保存したサイト別ルールを次回の設定取得で適用するため、タグの差し替えは不要です。すでに開いているタブへ即時反映する仕組みではありません。判断時に取得ルールの版が違えばJevへ進めず保留し、新SDKは設定を再取得してローカルデータを更新します。同じページの判断要求は再送しません。

ルールの版が変わると、ブラウザ内の以前の閲覧履歴を破棄して現在ページを取り直します。表示済み状態・許可済みのイベントや確定状態は維持します。旧SDKは新しい設定を解釈できないため、キャッシュ更新後の再読み込みが必要です。

右側へURLを入力すると、別タブのSDKから取得結果と理由を受け取れます。未保存の設定案でも確認できます。計測同意・最新版SDK・サイトのメタデータ送信有効化が必要です。確認中は通常判定・オファー表示・履歴保存を行いません。詳細は[サイト設定](../guides/sites#ページ情報の取得と実ページ確認)を参照してください。

### 従来モードの取得優先順位

まず、後述のルールでページを代表するJSON-LDオブジェクトを1つ選びます。各フィールドには、そのオブジェクトのプロパティを使います。

| フィールド    | 取得する順序                                                                           | 上限・値がない場合                                                |
| ------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `name`        | JSON-LDの`name` → `headline` → `title` → メタ情報の`og:title` → HTMLの`document.title` | 160文字まで。最終的に使える文字列がなければ`"Untitled"`           |
| `description` | JSON-LDの`description` → メタ情報の`og:description` → メタ情報の`description`          | 400文字まで。使える文字列がなければキーを省略                     |
| `type`        | 選択したJSON-LDの`@type`から、対応する種類を取得                                       | JSON-LDのみ。`og:type`等へのフォールバックはない                  |
| `themes`      | JSON-LDの`articleSection` → `keywords`                                                 | 各80文字まで、最大8件。JSON-LDのみで、`meta keywords`等は使わない |

メタ情報は`meta[property="キー名"]`と`meta[name="キー名"]`の両方を対象にし、文書内で最初に一致する要素の`content`を使います。たとえば`og:title`は`<meta property="og:title" content="…">`でも`<meta name="og:title" content="…">`でも取得できます。同じキーの複数要素は結合しません。

**次の候補へ進むのは、前の値が存在しないか`null`のときです。** 空文字・配列等の文字列でない値・後述の除外パターンに一致する値が入っていても、次の候補へは進みません。たとえばJSON-LDに`"name": ""`がある場合、OGPのタイトルがあっても`name`は`"Untitled"`になります。

`themes`は文字列または文字列の配列を受け取り、半角カンマ`,`で分割して整形します。`articleSection`と`keywords`は結合しません。`articleSection`が空文字や空配列の場合も、`keywords`へは進みません。テーマの重複除去は行いません。

### 従来モードのJSON-LDオブジェクト選択

対象は`script[type="application/ld+json"]`です。先頭10本を読み、1本の内容が100,000文字を超える場合やJSONとして解析できない場合は読み飛ばします。探索には深さ等の上限もあります。

対応する`@type`は次の9種類です。照合は文字列の完全一致で行います。配列で複数の種類が指定されている場合は、**その配列の記載順で最初に一致する種類**を採用します。

`WebPage`、`Article`、`NewsArticle`、`BlogPosting`、`Product`、`Service`、`JobPosting`、`Course`、`Event`

オブジェクトは次の順序で選びます。

1. `WebPage`の`url`または`@id`が現在のページと一致するものを探す。一致するものがなく、`WebPage`が1つだけなら、それを使う。
2. 選んだ`WebPage`の`mainEntity`が対応する種類なら、それをページの代表として使う。`@id`による参照は、読み込んだJSON-LD内の同じ`@id`を持つオブジェクトで解決する。
3. それが使えなければ、`url`または`mainEntityOfPage`が現在のページに一致する、`WebPage`以外の対応オブジェクトを探す。
4. 見つからなければ、手順1で選んだ`WebPage`を使う。
5. それもなく、`WebPage`以外の対応オブジェクトが1つだけなら、それを使う。複数あって特定できない場合はJSON-LDの代表を選ばず、各フィールドのOGP・HTML等の候補へ進む。

URLの一致はオリジンとパスで判断し、クエリ・フラグメント・末尾の`/`の違いは使いません。相対URLも現在のページを基準に解釈します。複数が一致する場合は、探索順で最初のものを使います。`mainEntityOfPage`はURL文字列、または`{"@id":"…"}`の形式に対応します。

探索するのはJSON-LDの直下のオブジェクト・配列と、その`@graph`・`mainEntity`です。`itemListElement`内の商品等は探索対象にしません。参照を解決するために外部URLへアクセスする処理もありません。

### 文字列の整形と除外

名称・説明・各テーマは、連続する空白や改行を半角スペース1つにし、前後の空白を除き、上限の長さに切り詰めます。その後、メールアドレス形式や、空白・ハイフンを挟む形を含む9桁以上の数字列に一致する文字列は採用しません。

このパターン検査だけで個人情報をすべて検出できるわけではありません。氏名・住所・個人向けの情報などをページのメタデータへ入れている場合は、収集対象から除外する等の対応が必要です。

### 取得例

現在のURLが`https://example.com/products/polo?from=mail#size`で、以下のJSON-LDがある場合の例です。

```json
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "吸汗速乾ポロシャツ",
  "description": "さらりと着られる夏向けのポロシャツ",
  "keywords": "吸汗速乾,ポロシャツ",
  "offers": { "@type": "Offer", "price": "3980", "priceCurrency": "JPY" }
}
```

取得する`page`は次の形です。`offers.price`や`priceCurrency`は取得対象に含みません。以下は説明用の例で、実サイトの計測結果ではありません。

```json
{
  "url": "https://example.com/products/polo?from=mail",
  "path": "/products/polo",
  "name": "吸汗速乾ポロシャツ",
  "description": "さらりと着られる夏向けのポロシャツ",
  "type": "Product",
  "themes": ["吸汗速乾", "ポロシャツ"]
}
```

画像URL、価格、在庫、パンくず、見出し本文、ページ全文、JSON-LDの`about`等は、この自動抽出では使いません。応募・予約・カート等の業務状態や独自クリックは、[任意の追加連携](./sdk)で登録した名前と値を明示的に渡します。

## ブラウザ内に保存するもの

sessionStorageの`jev:v1:<サイトID>`へ次の値を保存します。キー名は互換性のため維持し、内部の`version`は2です。現在ページの計測は`currentVisit: {page, visibleMs}`に保存し、有効閲覧になってから`visits`へ追加します。`entryPage`には流入ページ、`urlPolicyRevision`にはURL除外設定の版を保存します。サイトIDが`demo`なら、保存キーは`jev:v1:demo`です。

| キー       | 保存する値                                                       |
| ---------- | ---------------------------------------------------------------- |
| `visits`   | 最低閲覧時間を満たした`page`と`visibleMs`の配列                  |
| `actions`  | 任意連携した`{name, value}`の配列。値を省略した場合は`{name}`    |
| `facts`    | 任意連携した状態名と、真偽値または有限の数値の対応表             |
| `delivery` | 施策IDごとの`{shown, dismissed}`。表示成功回数と、閉じたかどうか |
| `updated`  | 最終保存時刻。`Date.now()`によるミリ秒の値                       |

再読込時は`updated`が30分以上前の保存データを復元せず、現在の許可経路・イベント名・状態名等でも再検証します。閲覧ごとの日時を保存して30分で削除する方式ではありません。別タブや別端末を1人の訪問者として結び付けません。

表示上限は全端末での恒久的な回数制限ではありません。ブラウザ内の有効な履歴に対する制限です。

取得ルールの版は`metadataRevision`として履歴とともに保持します。従来モードは`legacy`、標準・カスタムは取得設定のハッシュ（32桁の16進文字列）です。版が変わると以前の`visits`を破棄します。

## 判断時に自前APIへ送るもの

`POST /v1/decision?siteId=<サイトID>`のJSON本文に、次のキーを送ります。送信は判断のタイミングだけです。

| キー       | 内容                                                                            |
| ---------- | ------------------------------------------------------------------------------- |
| `siteId`   | 共通タグの`data-site`で指定したサイトID                                         |
| `visits`   | 閲覧履歴。各要素は`{page, visibleMs}`。過去の有効閲覧のみ。現在ページは含めない |
| `actions`  | 許可された名前で任意連携した行動。最新30件まで                                  |
| `facts`    | 許可された名前で任意連携した状態                                                |
| `delivery` | 施策IDごとの表示済み・閉じた状態                                                |

新版SDKは`protocolVersion: 2`、`currentPage`、任意の`entryPage`、URL除外設定の版`urlPolicyRevision`、取得ルールの版`metadataRevision`も送ります。APIが現在の版と照合するための値で、Jevへは送りません。取得元や候補の採用理由も、通常の判断要求・Jevには含めません。

`updated`は送信しません。診断パネルで扱う取得元情報（`sources`）も、通常の判断要求には含めません。各項目の取得元は[診断パネル](../guides/debugging)で確認できます。

自前APIの受入上限は、`visits`が50件、`actions`が30件、`facts`が20項目、`delivery`が100施策です。`page.path`は512文字まで受け付けます。SDKはパスをその長さに切り詰めず、超過した場合はAPIの検証で拒否されます。その他の上限は[設定と上限](../reference/configuration)を参照してください。

APIは許可/除外経路、有効な閲覧時間・件数、登録済みイベント名・状態名を検証します。SDKから送られたものをすべて無条件にJevへ渡しません。

## Jevへ送るもの

自前APIは現在・流入ページと有効な過去の閲覧から次の`state`を作り、設定された`model`と施策の`questions`とともにJevへ送ります。

| キー                                                    | 内容・変換                                                                       |
| ------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `state.last_qualified_page`                             | 有効な閲覧のうち、最後の`page`。名称・説明・種類・テーマ等は上記のキーを維持     |
| `state.browsing_history_oldest_first[].page`            | 最低閲覧時間と許可経路の条件を満たした`page`を、古い順に並べた配列の各ページ情報 |
| `state.browsing_history_oldest_first[].visible_seconds` | `Math.round(visibleMs / 1000)`で秒に変換した値                                   |
| `state.actions`                                         | APIで許可された行動名に絞った`actions`                                           |
| `state.facts`                                           | APIで許可された状態名に絞った`facts`                                             |
| `questions`                                             | `c0q0`等のキーに対する`{type: "noul", instructions: "判定質問"}`                 |

`state.current_page`は初期表示を判断する現在ページです。`state.entry_page`は保存済みの流入ページがある場合だけ含めます。どちらも「閲覧済み」の証拠とは区別します。過去の有効閲覧がなければ`last_qualified_page`を省略し、履歴は空配列にします。

最低閲覧時間が8,000ミリ秒なら、3,000ミリ秒の過去ページは新版SDKの履歴へ追加しません。12,000ミリ秒の閲覧は`visible_seconds: 12`になります。最低閲覧時間への到達時にはサーバーへ送らず、次ページの初期判断で使います。施策の必要履歴数を0件にすれば、過去履歴がなくても現在・流入ページで判定できます。

`siteId`、`delivery`、`updated`はJevの判断用`state`に含めません。どの閲覧を判断材料にするかはAPI側のアルゴリズムで調整します。条件不足・対象施策なし・キー未設定・費用上限等の場合は、Jevへ問い合わせずに保留します。

Previewの固定判定や配信前の強制プレビューでも、実際のJevへ送信しません。

確定条件・AND/OR・最終的な表示はコードが扱います。質問同士で他の回答を参照させません。

## そのまま送らないもの

フォーム入力、ページ全文、JSON-LD全体、フォームから氏名・メール等を自動取得する仕組みではありません。URLのGETパラメータは既定で送るため、含まれる値は除外設定で確認してください。基本メタデータにも個人情報が含まれる場合があるので、実サイトの情報と範囲を確認してください。

## サーバーの保存

閲覧者ID、閲覧者セッション、行動履歴DBは持ちません。管理者のユーザー・パスキー公開鍵・管理セッション・サイト所属・施策は、別の管理用DBへ保存します。

サイト専用Jevキーは暗号化して管理用DBの専用テーブルへ保存します。実Jevの呼び出し時刻・結果分類・モデル名・遅延・キー種別の運用記録も保持しますが、URL・閲覧者情報・送信内容・回答は含みません。[記録の定義と保持](../guides/jev)を確認してください。

Jevへの送信、CDNやプロキシのログ、Cloudflare Accessの認証ログまで存在しないという意味ではありません。外部サービスの保持条件・契約・設定も運用者が確認します。

診断パネルの情報も扱いに注意し、[秘密情報と運用](../operations/security)を併せて確認してください。

従来モードの取得順序は[旧SDKのextractPage](https://github.com/manji6/jev-personalization/blob/a51af0efb9b73cf6b5a117021403206099d5c9a3/src/sdk.js)。現在の自前APIの受入形式は[schema](https://github.com/manji6/jev-personalization/blob/main/src/schema.js)、Jev向けの変換は[engineのprepare](https://github.com/manji6/jev-personalization/blob/main/src/engine.js)に対応します。
