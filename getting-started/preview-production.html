PreviewからProductionへ ​

環境の更新は、確認用に配置して操作を確認し、許可したコミットだけを本番へ反映します。施策の「下書き→配信開始」とは別の、システム更新の手順です。

Previewと本番の違い ​

対象PreviewProduction
URL・パスキー確認用の固定Origin本番Origin
DB・ユーザー・施策確認用D1本番D1
Durable ObjectsPreview専用本番専用
Access許可された担当者に限定運用方針に従う
Jev初期構成は固定スタブ本番キーで実判定

CloudflareのWorker Previewsを使います。Version URLは本番リソースを共有するため、この分離確認の代わりには使いません。

1. 確認版を作る ​

設定・実装をコミットし、テストを通します。

sh
npm run check
npm run test:cloudflare
npm run test:browser
npm run cf:preview

スクリプトが本番と異なるDB、移行先、制限用namespace、認証設定を検証します。Previewだけへ移行と配備を行い、data/deployments/preview.jsonにコミットとDeployment IDを保存します。

固定のPreview URLを使ってください。個別Deployment URLはパスキーの登録先として使いません。

2. 確認する ​

  • Accessで入場し、パスキーの登録・再ログインを確認する。
  • 対象サイトを切り替え、権限を確認する。
  • 施策の下書き保存・配信開始・停止を確認する。
  • 同一Originのデモページで表示と共通デザインを確認する。
  • 画面上部の確認版コミットを控える。

スタブの0.95をJevの実測や施策効果として扱いません。実モデルの確認は別途キーと費用枠を設定したうえで行います。

Accessで全体を保護したAPIへ、外部サイトのSDKから認証Cookieなしで通信することはできません。現在の非公開Previewでは同一Originのデモを使います。外部サイトとの試験には、管理画面と配信APIの保護範囲を別途設計します。

3. 許可した版を本番へ反映する ​

確認が終わり、本番反映が明示的に許可された後に実行します。

sh
npm run cf:release -- --reviewed-commit FULL_40_CHARACTER_COMMIT_SHA

HEAD・作業ツリー・配備記録・Production設定のハッシュを照合し、未確認や未コミットの変更があれば停止します。短い7文字のSHAではなく40文字のSHAを指定します。

確認用のDB、アカウント、パスキー、施策を本番へコピーしません。本番側は本番データを使い、本番Originで初回登録します。

更新時の注意 ​

このリポジトリのCIは検査だけを行います。cf:deployも同じ確認を要求し、配備記録なしでは停止します。Cloudflare Buildsや別の外部CIに直接wrangler deployを設定している場合はこの確認を通らないため、自動の本番配備を無効にして手動リリースへ統一してください。外部サービスの連携設定は、コードの変更だけで自動的に解除されません。

配備記録がない新しい作業環境では、同じコミットをPreviewへ再配置して記録と確認を作り直します。複数ブランチを同時に試す場合はPreview名・D1・Origin・移行設定をそれぞれ分けてください。

本番のバックアップと切り戻しは更新・復旧を参照してください。
