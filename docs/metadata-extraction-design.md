# サイト別ページ情報取得：詳細設計

2026-11-02。承認済みの非公開モックv2に基づく実装。Productionへはレビュー後にリリースする。

## 目的と画面

サイト管理者・Superuserが「サイト設定 → ページ情報の取得」で、そのサイト共通の取得方法を設定する。基本設定・共通デザインと同じ階層のタブに置く。編集者・閲覧者は参照と人工データの確認だけができる。

標準はページ名を`og:title → HTML title → Untitled`、説明を`og:description → meta description → 省略`の順に取得する。空・不正な値、共通ガードで除外した値は次へ進む。JSON-LD・type・themesは標準では参照しない。

カスタムは優先順位付き候補を最大10件持つ。候補は有効状態、管理名、最大5条件、AND/OR、ページ名・説明の取得元/キー/接頭辞、説明欠損時の方針を持つ。上から条件とページ名を満たす最初の候補を採用する。追加・編集・複製・削除・上下移動・有効切り替えを提供する。保存前に影響を確認する。施策ごとの設定ではない。

右カラムの主導線はURL入力と「このURLで確認」。結果には名称・説明・候補ごとの採用/不採用理由・フィールドの取得元・APIへ送るページ情報を表示する。「同じページから再取得」は接続中のページへ明示要求を送る。人工データ入力は折り畳んだ補助機能とし、実ページの結果と区別する。保存前でも確認でき、設定案を変えたら古い結果を消して接続を終了する。

## データモデルと配信

`site.metadataExtraction`は任意フィールド。値は`{mode: "standard" | "custom", rules: [...]}`。候補は`id/name/enabled/combination/conditions/nameOutput/descriptionOutput/descriptionPolicy`を持つ。取得元は`jsonld/meta/title`、条件演算は`nonempty/exists/equals/includes`。出力は`{source,key,prefix}`、説明欠損は`allow/next`。スキーマは未知フィールド・重複ID・過剰件数・不正キーを拒否する。

共通`/sdk.js`にルール評価器を一度配信する。SDKは同意後、既存の`GET /v1/sites/:siteId`から取得ルールと`metadataRevision`を受け取る。管理画面での変更はDBのサイト設定だけを更新する。サイト別SDKの生成・ビルド・タグ交換は不要。設定に秘密を含めない。公開設定の応答はno-storeだが、配布済みのSDK本体は既存の5分キャッシュの影響を受ける。

revisionは、Zodで整形済みの取得設定をSHA-256にした先頭32桁。標準・カスタムとも同じ方式で計算する。条件順や無効候補の変更も版を変える。閲覧者識別子として使わない。APIは`input.metadataRevision`を検証し、違えばJevへ進めず`hold / metadata_revision_changed / metadataRevision`を返す。

SDKはその応答時だけ設定を再取得し、現在ページを取り直す。同意期間あたり最大2回の更新試行とし、定期ポーリング・無限リトライはしない。取得ルールの版が変わった過去の`visits`は破棄し、表示済み状態と許可済みのイベント・確定状態は維持する。生のJSON-LDを履歴へ保存しないため、過去ページを再抽出しない。応答の世代チェックで旧ルールによるオファー表示を防ぐ。

## 既存サイトの移行

フィールドがない既存サイトは`legacy`として従来の抽出を維持し、管理画面へ移行案内を表示する。新版SDKでも旧版リクエストでも、未移行サイトは従来どおり利用できる。新規サイト作成と同梱の設定例では標準モードを明示する。

既存サイトは管理画面で標準またはカスタムを選び、URLで確認して保存する。移行後は旧SDKの版なしリクエストを保留する。旧SDKには新しい評価機能がないため、キャッシュ更新後にページを再読込する。新標準としてJSON-LDの値を黙って受け付ける互換処理はしない。元の動作が必要なら移行前にそのサイトに合うカスタムルールを確認する。

## 抽出器

標準ではmetaのproperty/nameを同じキーとして扱い、文書内の最初の一致を使う。最大200要素を走査する。JSON-LDは必要なカスタム候補があるときだけ読む。先頭10本、各100,000文字以下、探索深さ8、オブジェクト最大200、各配列先頭100件。探索は直下・配列・@graph・mainEntityに限り、itemListElement・外部@context/@idは展開しない。

JSON-LD条件と取得値は必ず同じオブジェクトに結合する。条件を満たす候補が1件なら使う。複数なら現在ページと一致するWebPageのmainEntityを優先し、それで決まらなければ現在ページに結び付くURL/mainEntityOfPageが一意のものを使う。特定できなければ次候補へ進む。URLの比較はoriginと末尾スラッシュを除いたpathで行う。

`includes`は文字列・数値・真偽値を文字列化した完全一致で、部分一致ではない。配列は要素の完全一致。`ProductGroup`を`Product`とはみなさない。`exists`はundefined以外、`nonempty`はundefined/null/空文字/空配列以外とし、0/falseを欠損と扱わない。

出力は文字列のみ。名称160・説明400・種類80・テーマ8件×80文字。空白整形とメール形式/長い数字列の除外は接頭辞の結合後も適用し、無効化できない。全候補不成立なら現在pathとUntitledを残す。JSON-LD候補採用時は同じ候補からtype（@typeの先頭の文字列）とthemes（articleSection ?? keywords、半角カンマ分割）を得る。meta/titleだけの候補で補完しない。

キーは最大120文字、最大6段の単純なプロパティ参照。prototype関連キー、式、添字、JSONPath、正規表現、任意JS、DOMセレクターは受け付けない。フォーム・HTML全文・SKUなど条件確認用の生値は出力へ自動追加しない。共通ガードだけで完全な個人情報除去を保証しない。

## 実ページの取得確認

管理画面から任意URLをfetchしない。CORS・JavaScript実行後のDOM・SSRFの問題を避け、対象サイトに設置したSDKで確認する。

1. `POST /admin/api/v2/sites/:id/metadata-inspection`へURL・未保存の取得設定・32byte nonceを送る。既存のCookieセッション、正確なOrigin、CSRF、サイト管理権限を必須にする。
2. HTTPS（開発時localhostのHTTPのみ可）・登録origin・収集/除外path・メタデータ送信有効を検証する。実ページのquery/hashは表示に必要な場合があるため保持し、DBにはorigin/pathだけ保存する。
3. ランダム32byteのticketを生成する。DBにはSHA-256ハッシュ、管理者セッションハッシュ/ユーザー/サイト/origin/path/nonce/設定案/有効期限だけを保存する。5分間、1ユーザー最大20件の未使用ticket。期限切れは発行時に削除。ログアウト時はFKで削除する。監査は操作名とサイトのみでURLや結果を含めない。
4. 別タブのfragmentへ管理画面origin・nonce・元hashを載せる。ticketはURLに載せず、管理画面に保持する。SDKはマーカーを取り除き、queryと元hashを戻す。このモードでは通常SDKの収集・判定・表示処理を開始しない。不正なマーカーは通常配信へフォールバックしない。
5. SDKはサイトの同意を待つ。同意後、openerへreadyを送り、管理画面はsource/origin/site/nonceを検証してticketをpostMessageする。SDKも対称に検証し、targetOriginは固定する。
6. `POST /v1/metadata/redeem?siteId=...`でticket/nonce/現在pathを引き換える。登録originのCORS、ticketの束縛、現在のサイト設定・ユーザー・権限・セッション/版/有効期限を確認し、未使用→使用済みを条件付きSQL更新する。1回だけ設定案を返す。ルールや結果を通常SDK設定へ保存しない。
7. SDKが現在DOMを評価し、抽出結果と生の条件値を含まない根拠だけをpostMessageする。管理画面は信頼しない入力として扱い、HTMLエスケープして表示する。Jevは呼ばず、履歴・表示済み状態も保存しない。
8. メタ情報のDOM更新と明示的な再取得で結果を更新する。確認開始から5分、同意撤回、URL変更、終了操作、設定案変更で確認を終了する。更新操作には引き換え済みticketを再使用しない。

SDK未設置・旧SDK・同意待ち・期限切れ・COOP・CSP・ポップアップ制限を案内する。未接続だけで原因を断定しない。COOPでopenerが切れるサイトの中継方式は初期実装に含めず、人工データで確認できる導線を残す。iframe・ブラウザ拡張は不要。

## マイグレーションと検証

`0004_metadata_inspections.sql`をNode/Cloudflareで適用する。既存サイトbodyの一括変更、閲覧者ID・履歴DBの追加、キーの再発行は行わない。

テストは標準/カスタム、欠損/曖昧なJSON-LD、型の完全一致、AND/OR、原子性、上限、危険キー、版変更/履歴維持、CAS/CSRF/役割、ticketの束縛/再使用/失効、D1/workerd、実ブラウザの同意/DOM更新/未保存確認/偽メッセージ/モバイルを対象とする。APIとブラウザのモデルはテスト用で、実Jev呼び出しは行わない。実行結果は`metadata-extraction-validation.md`へ記録する。
