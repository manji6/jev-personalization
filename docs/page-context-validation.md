## 主な境界例

- 初期判断は最低閲覧時間を待たず1回。時間到達・長時間放置・track/setFact・メタ更新・decide再実行では追加要求なし。
- 非表示の初期ページは表示時に1回。応答受信時だけ非表示なら、状態を変えず表示再開したときに通信せず描画。
- SPAはpathname変更ごとに設定GETと初期判断を1回。queryだけの変更はローカル更新。query変更中の古い表示応答は破棄。
- 同意撤回、通信中の状態変更、離脱して同じパスに戻る競合で古い応答を表示しない。通信失敗・設定版不一致でも同じページでは再POSTしない。
- 現在ページ・流入ページを有効閲覧履歴と分離。URLのない初回ページを、後続ページで流入ページとして置き換えない。
- 除外キーの重複、URLエンコードされたキー、大文字小文字、資格情報、fragment、長すぎるURL、保存データの再検証を確認。
- 新しい除外キーで過去のURLと流入URLを再整形。APIでも除外し、Jev向けstateに除外値を残さない。異なるoriginやpathと不整合なURLは拒否。
- 過去の履歴0件・流入cid条件のみの初期判断に成功。Jev呼び出しと問い合わせ予算を使わない。Node版・Workers版の両方で確認。
- 管理画面で除外キーを独立保存し、URL条件の施策を下書きから配信開始まで操作。権限・CAS・従来の取得設定を維持。
- 実ページ取得の確認では、入力したURLのqueryを管理APIへ送らず、設定案の除外キーを対象SDKへ渡す。結果とチケットDBに除外値を残さず、対象ページは元のqueryで開く。
- 1440px・390pxの画面を撮影し、横方向のはみ出しがないことと設定フォームを確認。認証・診断・独自JavaScript・既存の表示形式も回帰確認。

## Previewでの確認手順

1. Access認証後、Previewの管理画面へログインする。本番と別のD1を使用する。
2. 「サイト設定 → ページ情報の取得」で`email`・`token`等の除外キーを指定し、右側へURLを入力して加工後を確認する。
3. 新しい施策の「対象者・条件」で「URLの確定条件だけで判定する」を選ぶ。過去の有効閲覧数は0件にする。
4. 「流入ページ」「GETパラメータの値」「cid」「含む」「runner」を設定し、表示コンテンツを入力してPreview内で配信開始する。
5. Preview用の確認ページを`?cid=mail_runner&email=sample`付きで開く。診断・Network・sessionStorageで、初期POSTが1回、emailが除外されることを確認する。
6. 最低閲覧時間を超えて待ってもPOSTが増えず、履歴だけが保存されることを確認する。次のページでは保存した流入cidが引き継がれる。

PreviewのJev方式は固定値のスタブ。URL条件は実際のコードで照合する。ヘルプの変更はソースとビルドを準備済みで、本番リリース前にGitHub Pagesの公開内容へ先行適用しない。
