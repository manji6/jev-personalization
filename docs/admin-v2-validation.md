- 公開SDK/設定/管理API/ログにキー・暗号文・閲覧情報を混ぜないこと。入力欄を送信時・再表示時に空欄にすること。
- workerd/D1で暗号化した専用キーを上流の固定URLで使い、再リクエストでも利用記録を共有すること。
- 実パスキー署名を使うブラウザ試験で、重要変更の再認証、確認画面、設定保存、利用状況、モバイルと直接URLでの権限拒否を確認。

画面例の件数・モデル・遅延は合成データです。所有者の実機パスキー、実Jev APIキーの有効性・実測速度・課金量、本番負荷の検証とは区別します。新機能のCloudflare Preview反映と所有者の最終確認は、配備時に別途記録します。

## 自動検証

Node.js24.19、Chromium（Playwright）、SQLite、Miniflare/workerdを使用します。WebAuthnは仮想CTAP2のdiscoverable credentialで、実際に署名を生成してサーバーで検証します。画面の認証を成功したように見せるスタブではありません。

| npm run check                           | 既存32件と追加の管理API10件、計42件                          |
| npm run test:cloudflare                 | 既存8件と管理DB/切り替え保護2件、計10件                      |
| npm run test:browser                    | 既存54件と新画面/認証/localhost11件、計65件                  |

最終実行はすべて成功しました。自動テストは合計117件（42＋10＋65）です。format:check、Cloudflare dry-runも成功。本番依存のnpm auditは既知の脆弱性0件でした。Workerのdry-runサイズはgzip 313.22KiBです。以下は確認した受入範囲です。

- 初回Superuser登録、Secure/HttpOnly Cookie、実署名での再ログイン、表示名の保存/再読み込み。
- Node.jsだけでなくworkerdでのWebAuthn登録・認証、challengeの再利用拒否、ユーザー検証UVがない署名の拒否。
- 旧Bearerトークンで新管理APIへ入れないこと、固定Origin/CSRF、未所属サイト・閲覧者・編集者の権限拒否、所属解除とユーザー停止の反映。
- 最後のSuperuser・最後のパスキー保護、重要操作の再認証、無操作/絶対期限。
- 手動招待、新規パスキー登録、複数所属を支えるAPI、受諾済みリンクの拒否、招待者の権限取消。
- 復旧コードでのパスキー再登録、旧パスキー・セッション・残りのコードの無効化。
- 途中の下書き保存、配信データの維持、判定質問の固定テンプレート、明示的な配信開始、古いrevision拒否、下書き破棄。
- URL制限・Origin・期限・revisionを検証する1回限りの実ページプレビュー。並行取得も1件だけ成功。
- 停止中の標準/独自JavaScript施策を実ページで表示し、preview modeを渡すこと。通常のJev呼び出し・sessionStorage更新・表示回数加算をしないこと。
- SPA遷移で確認表示を除去し、通常配信との二重表示を避けること。
- 新管理画面から実際に診断パネルへ接続し、サイト権限付きの認可を受け渡せること。
- 既存SDKの同意・メタデータ取得・イベントによる判断、通常オファー・デバッグパネルの回帰。
- 本物のlocalhost HTTPサーバーで、Secure Cookieとパスキーが動くこと。公開用サーバーは起動しないこと。
- 移行済みのWorkerでAUTH_MODEがなくなった場合、旧共通トークン方式へ戻らず失敗すること。

スクリーンショットも実API・一時DB・仮想パスキーを使った画面です。`node scripts/capture-admin-v2.js`で再生成できます。外部のJevや公開環境を呼びません。

## 利用者による最終確認

[ローカル起動](manual.md#1-公開せずに一通り試す)後、実際に利用する端末のChromeまたはEdgeで以下を確認してください。初回登録時の端末の認証ダイアログはOSによって異なります。

1. 自分の表示名とメールで最初のパスキーを登録し、ログアウト→同じパスキーでログインする。
2. アカウントで表示名を変更し、予備パスキーと復旧コードを登録する。
3. 施策を作り、案内する内容と対象者を入力して、Jevへ送る質問が意図に合うか確認する。
4. 表示タイトル・本文・形式・表示対象を設定し、下書き保存する。保存だけでは配信開始されないことを確認する。
5. 一覧のプレビューから`http://localhost:4174/demo`を開く。確認表示と終了を試す。画像はHTTPSの表示できる画像URLを使う。
6. 共通デザインでモーダル・フローティング・通知バーを切り替えながら色・余白を確認する。
7. 配信開始・停止・再開を試す。ローカルの通常判定は固定スタブ0.95であり、Jevの精度確認とは区別する。
8. 必要なら別のメールで招待リンクを発行し、別のブラウザプロファイルで受け、閲覧者/編集者の権限を確認する。
9. Superuserでサイト追加・ユーザー管理・環境名/予算を確認する。最後のSuperuserは無効化できない。
10. 「動作確認」からデモページの診断パネルを起動する。

対象ページURLが表示条件外なら拒否されます。例として完全一致`/ja/`の施策を作った場合、ローカルの`/demo`へはプレビューできません。ローカル確認では`/demo`または全許可ページを対象にしてください。

## 未実施・保証しない範囲

実際のTouch ID/Face ID、物理セキュリティキー、iCloud/Google/Microsoft等の同期サービス、Safari/Firefox、利用者ごとの企業ポリシーや端末管理は自動テストしていません。RS256を受け付けますが、今回の仮想認証器での署名実測はES256です。

この作業では本番サイトへの設置変更、メール配送、課金が発生するJevの新たな実リクエスト、公開版のDB移行、大規模負荷試験、外部のセキュリティ監査を行っていません。以前の少数のJev実測は今回の認証・UIテストの結果と混ぜません。

一般公開へ進める際は、上の実機確認と対象サイト固有のCMP・CSP・COOP・SPAの確認を先に行い、[運用手順](admin-v2-setup.md)に従って切り替えます。
